## 13. 原任务现场纠错与恢复

已确认的边界：纠错属于原任务的执行闭环，包括必要的继续执行和材料补全；由后置 Validator／Reviewer 发现的问题也应回到对应原任务或评审步骤处理。纠错不新增任务级补检轮次，不以最终证据数量不足为唯一启动条件。已有足够有效卡时，发现的执行问题仍需处理或明确记录其处置结果。

“纠错结束”不等于一定修复成功，而是适用动作已执行并复核，或已有明确的不可恢复、次数／预算耗尽等停止原因。不能仅生成恢复建议就视为完成；也不能为获得有效卡无限重试或放宽校验。

### 13.1 按问题整理纠错范围

| 问题或现场状态 | 原任务内应执行的处理 | 必须记录和复核的结果 |
| --- | --- | --- |
| 查找材料失败、任务未实际完成检索 | 根据具体失败修复调用或恢复执行，必要时有限重试／换已启用来源 | 是否实际执行、失败对象和原因、恢复后是否产生候选；技术失败不能记成零命中 |
| 查询执行成功但零候选 | 检查查询表达、条件及策略，按需在原任务内重新规划和执行 | 原查询与新计划、调整原因、各次候选数、结束原因；零命中是观察结果，不自动认定为工具故障或新颖性成立 |
| 获取材料失败、文件缺失或内容不可读 | 核对来源记录和文件状态，按失败类型恢复获取／解析／读取，必要时有限重试或换来源 | 来源、材料及文件关联、失败环节、恢复后的可读性；不能只以下载请求成功作为完成 |
| 已有候选未读、已有摘要但需要全文 | 补读绑定材料，或获取并阅读所需全文 | 读了什么、材料版本、是否形成可用证据、原问题是否解决；正常按需读取也不计为任务级补检 |
| 证据构建或补正失败 | 向补正步骤传递具体拒绝原因，修正证据草稿；必要时回读真实材料，再次构建 | 原始拒绝、补正动作、再次构建结果、未解决原因；保留已有有效成果，不制造引用或位置 |
| Validator 拒卡 | 将具体检查失败反馈给原任务，针对可修复问题补正并重新提交 Validator | 原卡与修订产物关联、拒绝原因、重新验证结果；不可修复的卡保留拒绝状态 |
| 工具选择、参数、作用域或调用错误 | 反馈实际错误，纠正工具选择／输入，或恢复可用工具；在既定权限内重新执行 | 错误调用、修改内容、实际执行结果及下游验证；工具返回成功不等于证据有效 |
| 网络、限流、来源服务失败 | 按错误类型和允许范围有限重试或换已配置来源 | 每次尝试、退避、来源变化、结果及停止原因；不把换来源或重试包装成完整补检 |
| 模型输出、Reviewer 单卡／汇总或 Gate A 校验失败 | 修复具体输出，或恢复对应检查点和评审步骤；重新校验受影响产物 | 具体校验错误、已保存局部成果、修复／恢复及复核结果；技术失败与语义证据不足分开 |

## 14. 任务级补检

已确认的边界：补检是在同一次运行中针对已有查新点追加完整 `ResearchTask`，重新经过 Planner、Researcher、Validator 和 Reviewer，并合并有效成果；不重新解析论文或改写查新点。补检任务本身也需要执行第 13 节的现场纠错。

只保留两个触发条件，满足任一即可进入补检判断，但实际执行仍受轮次及全局预算等硬限制：

1. **数量不足兜底**：原任务必要纠错结束后，最终有效证据卡数量仍低于配置门槛。包括纠错已执行但仍没有有效卡的情况，不要求先证明存在新的语义研究方向。
2. **Reviewer 语义证据不足**：最新有效 Review 的 `status=insufficient_evidence` 且 `incomplete_reason=semantic_evidence`；数量达标也可触发。单独的补检建议、技术失败或材料不可用不等同于该条件。

2026-10-17 代码核对：`plan_recovery()` 已检查上述数量与语义入口，但其后仍混合选择局部恢复和完整研究任务。`_targeted_supplement()` 会把局部动作也包装为 `ResearchTask` 并递增同一 `rounds`；正常主线优先走该规则路径，`Coordinator.plan_supplement()` 仅在没有 `recovery_decisions` 时调用。现状不能视为已实现本节设计。
