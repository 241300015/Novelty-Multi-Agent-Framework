## 2026-10-27：Planner 概念与策略拆为 Harness 控制的两个阶段

核对旧实现：此前同一次 LLM 响应同时返回概念与策略，随后程序编译表达式；不存在“先完成概念提取、分类，再生成策略”的模型调用边界。因此英文别名的结构纠错通过，不能证明它与所属概念一致。

按本次确认已拆分：

1. Harness 提供当前 NoveltyPoint（含 claim、claim_en、technical_features）与 ResearchTask，调用概念提取；只接受概念角色、词项、别名、排除词和重要性。结构及既有词项规则不通过时，在本阶段修复。
2. 概念接受后由 Harness 冻结目录并发放 C1..Cn，再调用策略生成。模型只提交级别与概念编号；枚举来自已冻结目录，不能新增或回写概念。最后由 Harness 合并并确定性编译。

阶段转换由 Harness 自动执行，只告知模型当前阶段，不增加选择/确认调用。正常两次调用；`max_attempts` 改为每阶段上限（默认 3），因此每任务最多 6 次，仍受已启用的运行级预算约束。概念失败不启动策略；策略失败不重启提取。临时“无改动反馈，最多再一次协议纠正后退出”保留在各自阶段内，不重置循环预算。

纠错字段附带当前值与所属概念上下文，完整重建也使用当前阶段 schema；策略修复不能获得概念编辑权限。Runtime 记录阶段、冻结目录、SHA256 与各次修复，最终计划沿用原持久化和派发屏障。

验证边界：本次是接口和控制流实现，未运行真实模型完整实验，**英文别名的语义正确性仍待验证**。本次输入为上游查新点与任务，未新增读取论文全文的调用；不能将“有查新点原始表述”称为“已提供全文”。重复扩写和截断也未因两阶段拆分而得到解决。

实现：[Planner Harness](../../backend/src/novelty_agent_framework/core/planner_harness.py)；测试：[两阶段边界](../../tests/test_planner_two_stage.py)；流程与预算：[data_flow.md](../data_flow.md#planner-的两阶段-harness-与受控修复)。

离线验证：Planner／编译器／字段纠错／Reviewer 合同回归，以及配置注入、启动预检和提示词清单检查合计 **239 passed，3 deselected（6.28 秒）**。覆盖同步/异步双调用、概念失败屏障、策略字段与编号约束、冻结目录防修改、并发隔离、取消和运行审计。测试使用模拟模型与虚拟 provider 凭据，没有真实模型或检索请求。3 项集成测试在本沙箱挂起后从最终命令排除，不能记作通过：补检 Planner 失败保留既有结果、PDF 服务处理前构造工作流、自定义 Extractor/Coordinator 提示词全链路。补检测试诊断停在 asyncio Runner 退出；沙箱外执行申请及一次重试均因自动审批超时未启动。

## 2026-10-27：读取定位归还 Harness／Runtime

确认 Reviewer 的 `read_id` 错误来自模型接口职责划分：输入过滤了历史读取标识，但提示词和草稿 schema 仍允许模型提交读取标识及字符范围；读取返回、状态和汇总投影也保留了内部定位字段。跳过回读后仍生成这些字段，最终被授权检查拒绝。不是通用 Reader 读取失败，也不应通过要求模型更准确地填写内部标识来解决。

已实现以下调整，覆盖当前受控流程和旧原生调用路径的结果生成：

- 单卡模型草稿移除 `read_citations`，提示词只要求通过已提供的 `evidence_id` 表达判断依据。
- 后续补齐选择契约：`evidence_id` 也不能自由填写。Harness 发放 `evidence_options`，引用字段使用相同候选枚举；回读后动态更新，预算收尾和纠错同步使用最新候选。汇总只提供实际展示了非空引文的证据，空候选时引用数组必须为空。模型仍返回未发放编号时，后置检查拒绝并提供一次受预算约束的纠正机会。
- Harness 继承已有 Card/Evidence 绑定；回读得到非空授权文本后，在模型继续判断之前登记新 Evidence，提供原文与 `evidence_id`。原文、材料来源、字符范围和读取标识均由程序填写。
- 初始材料、受控状态、读取观察和汇总模型投影过滤内部读取标识与定位字段。原生工具模式的读取请求仍沿用原工具参数；其读取结果与判断草稿同样使用 Evidence。
- Runtime 回执、持久化结果和 checkpoint 保留完整溯源信息。历史结果解析保留兼容；不再把历史读取标识作为新模型草稿的引用入口。
- 注册读取事实不等于认定技术支撑关系：未被模型用于判断的读取内容仅作为背景证据，保留 `semantic_support=unassessed`。

实现见 [reviewer_evidence.py](../../backend/src/novelty_agent_framework/core/reviewer_evidence.py)；流程约定见 [data_flow.md](../data_flow.md#7-reviewer先接受初判再决定是否回读)。离线回归 **307 passed**，覆盖受控/原生调用、不回读、在线获取后读取、汇总恢复、内部字段不进入模型输入，以及材料/范围/checkpoint 篡改拒绝。本轮未运行本地模型完整实验，未重新验证生成质量或上下文用量；Coordinator 跨点绑定和 Researcher 质量问题仍待处理。

已实现的边界：

- 读取缓存也通知 policy 推进状态，沿用原观察；不新增物理读取、证据回执或读取额度消耗。受控文本选择和受控原生选择共用阶段说明。

临时纠错规则：Researcher 配置 `repeat_error_limit=2`。同一次 Harness 调用内，以**当前阶段＋当前选项集合＋错误码**识别重复决策错误；第一次拒绝给出纠正反馈，同阶段同类错误再次出现则退出决策循环，并尝试一次无工具结果生成，保留实际工具观察。任务标记 partial，记录原错误码及临时退出原因。若最终格式仍不合法，外层既有一次格式修复仍适用；这不是重新开放动作循环。

覆盖受控动作阶段的未知／过期选项、混合格式、提前提交结果和非法原生调用。新阶段不继承旧阶段的错误次数；成功零命中、没有新增候选、工具故障、预算不足均不计入该计数。通用 Harness 默认关闭此阈值，未统一改写 Reviewer、Planner、Coordinator 的纠错规则。Planner／Coordinator 已有“修复无实际改动”检查暂时保留，仍属于待研究机制。

**待研究问题：** 错误码一致不等于语义上完全相同的错误；阈值 2、反馈形式、是否应继续修复及其他退出方法，都没有实验结论。此机制控制失败循环长度，不能替代阶段修复，也不能证明生成质量提高。重复生成、引句失真、来源混淆、截断与别名语义错配继续分别跟踪。

验证：相关离线回归 **435 项通过**，覆盖 Researcher、共享 Harness 以及 Reviewer／Planner／Coordinator 相关边界。

回归入口：[阶段一致性与临时纠错测试](../../tests/test_research_stage_consistency.py)、[读取状态机测试](../../tests/test_research_reading_policy.py)、[自动检索测试](../../tests/test_initial_research_search.py)。本次使用离线模型与工具替身，未运行真实模型完整实验；上下文溢出与生成质量仍需后续真实运行观察。

### 需单列的设计与边界风险

- **确定动作仍要求模型确认。** 已选全文的首段/下一段、指定材料恢复读取、指定文献恢复获取，当前仍可通过仅有一个选项的菜单调用模型；正文续读不能跳过，却仍要求模型选择继续。这与“程序确定的流转由 Harness 执行”的方向存在张力，建议审视是否直接执行并通知。不能因此把“是否获取全文”等真正的内容决策也自动化；本轮未改变这些交互。
- **读取缓存旁路未通知 policy。** 缓存命中后直接返回观察并 continue，不经过 `policy.observe`；若受控 policy 在某状态需要再次消费同一片段/已知 EOF 来推进，菜单可能滞留。静态路径已确认，但本轮未在标准 ResearchReadingPolicy 的自然轨迹中复现卡住，不能列为已发生故障。后续共享 Harness 修改须验证缓存返回与新工具返回对状态推进的一致性，且不能把缓存复用登记为新物理读取。
- **错误循环不只来自混合对象。** 受控模式收到原生 tool_calls、动作阶段提前提交结果、未知或过期选项等拒绝分支，均可能反馈后继续循环，仅受总轮次限制。这是同一通用重试结构的其他入口，不代表本次实验已分别发生多次循环；如何纠错仍按前文用户保留意见另行研究。

没有发现需要让模型填写底层检索配置或读取定位的理由。正常工具观察会先记录再推进 policy；阶段推进异常保留已完成工具轨迹，取消也不会被当作成功。应保留这些已有边界。

后续实施应优先统一“阶段事实 → 当前可执行动作或自动操作 → 当前模型输出契约”，同时覆盖正常完成、预算收尾、能力缺失和缓存返回。单纯在所有拒绝分支添加次数阈值，无法修复以上状态/契约不一致。本节只筛查和记录，未改业务代码、未运行真实模型完整实验。

## Harness 与纠错机制核对

进一步核对实际请求和实现后，以下问题应同时作为 Harness 契约缺口记录，不能全部归为模型生成质量：

- Reviewer 选项阶段请求使用 `response_format=json_schema` 约束当前 `option_id`；单卡最终草稿、汇总及其格式修复请求没有相应生成约束，只在提示词中提供 schema，生成后再校验。`llm_0083/0084` 都将 `relation` 允许的 `unknown` 填入不允许该值的 `basis_type`；修复请求已经包含具体校验错误，但没有修正该字段。
- `ReviewerSummaryDraft` 的条件必填规则仅写在 Python `model_validator` 中。实际导出的 JSON Schema 只要求 `novelty_point_id/status`，允许结论字段为 null，未表达 `status=reviewed` 时结论字段必填。因此模型收到的契约与运行时校验不完全一致。
- 单卡输入提供 `feature_catalog`，汇总输入却未提供该固定目录；运行时仍按 `F1…F6` 校验。`llm_0085/0086` 使用 `f1/f2`，最终被引用校验拒绝。此处应补齐输入目录和字段候选约束，不能让模型猜测程序持有的标识。
- Researcher 引句错误有独立的一次修正机会：提交被拒卡、错误原因及实际 Reader 文本，要求逐字选引，再交 EvidenceBuilder 重新校验。本次修正未恢复被拒卡。校验层确实拦截了不匹配引句；当前自由生成引句的契约仍让模型承担了原文复制工作，后续可研究由模型选择原文片段、运行时提取原文和填充溯源的方式，保持 Reader 通用性。
- Planner 并未缺少纠错调用：错误检测 → 下发问题、修复建议和 `allowed_paths` → 模型选择修复并返回草稿 → 校验修改范围 → 重新编译。本次 `llm_0093/0094` 均返回未改动的别名，审计 `changed_paths=[]`，重新编译失败，终止原因为 `repair_budget_exhausted`。
- Planner 已有按字段编号提交更新的协议，但只有修改越界时才进入；原样返回不会触发该协议。当前缺少对无实际改动的修复进行专门反馈的分支；合法字段中的字符串仍可含中文，语言规则由编译阶段执行，不在生成 schema 中。下一步应优先评估首次纠错即使用字段级更新、无进展检测和受预算约束的反馈，而非简单增加完整草稿重试次数。

## 经确认后的实现与验证
