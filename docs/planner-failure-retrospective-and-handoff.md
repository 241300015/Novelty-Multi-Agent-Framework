# Planner 双阶段重构：失败复盘与后续开发交接

核对日期：2026-11-08。本文依据 Novelty / planner 开发对话《实施 Planner 双阶段重构》《调查重构验收并说明 DS API》、当前源码和本次精选实验归档整理。只保留项目相关结论，不复制私人对话。本文说明架构边界与验收要求，不指定必须照搬的实现目录或模块数量。

## 1. 当前交付状态

当前分支为 `refactor/planner-two-stage`，代码基线为 `c9128c79e90ba91c49937a265a0c7ff6f71326df`。11 月 2 日的新一轮实现已经按要求冻结并回滚；仅恢复了[实施与验收方案](planner-two-stage-implementation-and-acceptance.md)。本次归档不恢复已回滚源码，不修改 main，不表示新设计已经实现。

当前源码具备：

- Harness 先生成概念、做 schema 和确定性检查，冻结概念目录，再生成引用目录的策略。

## 2. 为什么上一轮不能算成功

### 2.1 业务操作没有明确绑定到 Agent 方法

上一轮主要通过 operation 字符串、通用 Adapter 和多个 Pipeline 定义生成、复核、纠错。SearchPlannerAgent 逐渐退化为入口，理解一次业务操作需要跨多个文件追踪输入构造、Prompt 选择、返回契约和采纳逻辑。

项目开发讨论已明确：应先确定“业务操作 → Agent 方法 → 明确输入输出、Prompt 与模型调用”，再由 Harness 编排。问题不是模块数本身，而是操作归属不清、重复组织调用体系、偏离仓库现有模式，造成可读性和维护成本恶化。此前先拆模块、后补接口边界的顺序不宜重复。

### 2.2 复核实际执行，但语义错误仍被接受

[精选失败数据](experiments/20261108_planner_failure_handoff/README.md)保留两轮本地 Qwen 记录：

| 批次 | 实际派发 | 已进入任务 | 结论 |
| --- | ---: | --- | --- |
| live-20261102-001 | 40 | DSGNN A1、A2，A3 中途 STOP | 语义不达标，后续矩阵及注入未执行 |
| retest-20261102-002 | 25 | DSGNN A1，A2 初审前 STOP | 修改通用语义 Prompt 后仍错误放行 |

典型错误：
1. 将不同机制或角色放入同一 terms，编译后按 OR 当作可替代词。第二轮 C3 包含“基于图摘要技术”“小批量训练”“注意力层”，初审仍返回 pass。
2. 初审漏检后，内容进入冻结通过集，后续局部纠错只处理 unresolved，因此不会再次触及这些错误。
3. 第二轮三个档位实际均为 `(C1 OR C2 OR C3) AND (C5 OR C7)`；“注意力层 + 工作节点”即可命中，不能保留该查新点的核心机制，仍被接受。
4. 有复核理由把等价表达式描述为已放宽；遗漏问题也曾要求原输入未提供的实现细节，局部复核随后又否定该要求。

历史调查核对了新上下文、v2 Prompt、原查新点和展开表达式均已提供。已派发响应结束原因为 stop，没有 length 截断证据。不能将问题简单归因于“没调用复核”或“再加一句 Prompt 就能解决”。同模型相关错误是待验证假设，未通过对照实验确认为唯一根因。

### 2.3 机械验收与语义验收混淆

mechanical_audit=verified 证明调用、决定与正式产物一致，不证明模型的 pass 正确。离线 fixture 证明给定判断后的控制流程，不能替代真实错误检测能力。

历史统计还存在口径问题：STOP 中断但有终态的任务计入完成数、未执行与不达标共用分类、独立语义审阅未接入汇总 pending 状态。程序 batch_accepted 并未变成 true；“整体完成”的报告不准确。

历史 1975 / 2023 / 2047 项离线通过属于已经回滚的不同实现快照，不能写成当前源码通过，也不能相加。另一路 GSAERU / Museformer 产物仍标为待人工评审，不能据机械完成认定质量通过。

## 3. 后续架构要求

### Agent：承载有名、有类型的业务操作

- 概念生成、概念复核、局部纠错、策略生成和策略复核，应在 Planner 自身的方法上明确表达；例如 `planner.review(...)`，具体命名、拆分和同步／异步接口由实现者探索。
- 方法接收本次操作所需输入，负责对应 Prompt、模型调用和结构化结果。复核使用新上下文。
- 公共模型设施只负责传输、解析、计量和记录，不接管业务操作定义。
- Planner 复核不是文献 EvidenceReviewer 的职责，检索工具也不应重新规划。

### Harness：拥有每次任务的控制状态

- Harness 控制阶段、候选标识、问题集、通过集、预算、确定性校验和最终采纳。
- 每次 task 调用的状态不得放在共享 Planner 实例上；并发任务必须隔离。
- Workflow 继续通过 `plan()/aplan()` 获得最终可交付计划，不能将它悄悄改为未复核草稿。
- 参考现有 Coordinator 的“Agent 方法 + Harness 编排”，但不要声称全仓所有 Agent 已统一为该形式。

### 契约、配置和表达式

- schema 明确操作输入输出、复核项及决定。两个现有 factory/配置入口均应正确注入 Prompt 和参数，避免旁路配置。
- 表达式生成语义与确定性解析、引用校验、资源限制分开；不要为方便实现而用固定模板替代新方案允许的模型逻辑。
- 不预设必须引入新的 Pipeline、Adapter 或运行框架；先复用当前模块和公共能力，只有职责确有必要时再拆分。
- 架构改进不等于复核质量改进，二者分别验收。

## 4. 具体实现可自主尝试，但必须验证

以下是待实验验证的建议，不是已完成能力，也不是唯一方案：
- 把词项/别名是否可替代、原文机制覆盖、依据和不确定性变成可核对的复核项；检查分项与总决定一致。
- 让策略复核检查受资源限制的充分命中组合，区分“出现核心词”与“所有合法命中路径保留必要机制”。
- 区分问题已修复、问题不成立、问题未解决；不把复核改口记为修复成功。
- 初次接受前强化门槛。若重新打开通过集，必须明确这是状态机和预算契约变更，不能偷加在局部补丁中。
- 分开记录未执行、中断、机械通过、语义失败、待人工确认。格式合法且理由非空的错误 pass 应成为回归样本。

保留[原方案](planner-two-stage-implementation-and-acceptance.md)的语言、局部隔离、预算、部分结果、持久化和验收目标。实现前补齐操作映射、输入输出和配置接线设计，再做小步代码与对照实验。不要把固定样本答案写入 Prompt。

## 5. 建议从 main 新建纯净分支

建议在实施时获取最新 main，再从它新建独立分支和工作树。本交接分支保存历史与证据，不建议整体合入或直接作为下一轮开发基线。

核对时远端 main 为 `7ff63dd061db0470cd15462e85d20ae3af40c180`；这是观察值，不是要求长期固定的起点。当前 Planner 分支相对本地 main 有八个未包含提交，其中还涉及 Reviewer、Coordinator 和 Harness 等前序改动，直接搬运会扩大重构范围。

新分支先确认 main 的现有接口、依赖和测试基线，再逐项移植必要能力，保持当前代码管理和组织方式。设计文档和失败样例可作为参考；已回滚源码、整体补丁和旧快照不能未经评审直接恢复。
