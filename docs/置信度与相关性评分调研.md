# 置信度、相关性与 Validator 职责调研

日期：2026-10-17。依据：当前正式后端源码、已有测试及本次本地回归。

## 1. 结论

Card 的置信度（confidence）和相关性（relevance）主要由 Researcher 模型直接填写。
目前没有统一的评分公式、分档标准或基于已标注数据的校准过程，不能把 0.8 理解成
“经过测量，有 80% 的概率正确”。0～1 只是数值范围约束。

本次按职责调整：Validator 删除置信度和相关性的最低分数阈值，继续检查字段格式、
任务归属及落盘溯源。低分但合法的卡可以进入后续评审；高分也不能使来源不合法的卡通过。
字段本身和报告展示仍保留。是否继续使用这些分数、如何定义评分标准，是后续设计问题。

## 2. 分数从哪里来

正式路径由配置工厂创建 `TaskResearcherWorkflow`。它将当前查新点、任务、检索计划和
`ResearchFinishDraft` 的 JSON Schema 提供给模型，Harness 的执行观察也进入当前任务上下文。
模型结束研究时，输出包含卡片和引文的草稿。

| 字段 | 谁填写 | 含义与当前限制 |
| --- | --- | --- |
| `EvidenceQuoteDraft.confidence` | Researcher 模型 | 单条引文及解释的评分；当前 Schema 没有给出更细的评分定义。 |
| `EvidenceCardDraft.confidence` | Researcher 模型 | 整张卡语义判断的评分；没有代码从引文数量、完整性或检索覆盖计算它。 |
| `EvidenceCardDraft.relevance` | Researcher 模型 | 候选文献与当前任务的相关程度；不是数据库排序分数，也不是由向量相似度计算。 |

三个字段均为必填、范围 0～1。当前两个正式 Researcher Prompt 要求依据读到的原文进行比较，
区分“未提及”与“不存在”，但没有规定 0.3、0.6、0.9 各代表什么，也没有评分校准样例。
因此不同任务、模型或提示词版本给出的数值，不宜直接当作可比的客观度量。

源码：

- [草稿字段](../backend/src/novelty_agent_framework/schemas/research_tools.py)：`EvidenceQuoteDraft`、`EvidenceCardDraft`。
- [输入和草稿解析](../backend/src/novelty_agent_framework/workflows/research_task.py)：`_render_prompt`、`_parse_finish`。
- [纯选项 Prompt](../backend/src/novelty_agent_framework/prompts/research/choice_only.md)和[原生工具 Prompt](../backend/src/novelty_agent_framework/prompts/research/native_tool_loop.md)。

## 3. Builder 是否重新计算分数

普通单文献卡不重新计算：

```text
Evidence.confidence = 引文草稿 confidence
Card.confidence     = 卡片草稿 confidence
Card.relevance      = 卡片草稿 relevance
```

Builder 确定性完成来源绑定、引文匹配和位置计算，但这些核验结果不会被换算成新分数。
能编译成功不等于分数得到验证；卡片的置信度也没有被强制限制为其引文置信度的最小值。

只有来源唯一、允许拆分的多文献混合草稿存在特殊处理。每个子卡的置信度为：

```text
子卡 confidence = min(原卡 confidence, 属于该子卡的各条引文 confidence)
子卡 relevance  = 原卡 relevance
```

例如原卡置信度 0.9，某子卡的两条引文置信度为 0.8 和 0.6，则子卡为 0.6。
这只是保守取最小值，没有引入新的独立判断。拆卡后相关性仍沿用原卡，没有按各篇文献重评。
同时 Builder 会清空不能可靠归属到单篇文献的 overlaps、differences 和 baseline 标志。

源码：[EvidenceCardBuilder](../backend/src/novelty_agent_framework/tools/evidence_card_builder.py)，
包括 `build` 的拆分逻辑和 `_build_card_items`。

格式修复和引文纠错可能让模型重新返回带分数的草稿，但它们不是专门的评分校准流程。
纠错结果重新经过 Builder；已有有效卡的合并也不是对分数做平均或加权。

## 4. 后续如何使用这些分数

### Validator

调整前默认 `minimum_confidence=0.3`、`minimum_relevance=0.3`，任一分数低于阈值即拒绝。
这相当于用模型自报的分数决定是否允许其证据进入评审，超出了本次确定的机械合法性职责。

调整后删除两项配置及拒绝分支，分数为 0 的合法卡也可通过；超出 0～1、NaN 等仍不符合字段契约。
本地调用方不应再向 `EvidenceValidationConfig` 传入已删除的两个参数。
仓库中的运行配置未发现这两个参数的接入，原先使用的是 Python 默认配置。

源码：[DefaultEvidenceValidator](../backend/src/novelty_agent_framework/agents/evidence_validator.py)。

### Reviewer 与报告

Researcher 的卡片分数随 Card 传给 Reviewer，但正式单卡评审和 NP 汇总还会分别生成
Review 自己的 `confidence`。它们是模型对当前评审输出的评分，不是把 Card 分数自动求平均。
状态为 `reviewed` 时要求有裁定、理由和置信度；证据不足状态不能保留正式裁定。

仓库另有兼容接口的 `reviewed_confidence`，其提示词说明为“原卡实质判断被输入证据支持的程度”，
不覆盖原卡分数。它和正式 NP Review 的置信度不是同一个字段，不能混为一套计算。

报告组装将正式 Reviewer 的置信度绑定到对应结论；Renderer 分别展示 Card 的相关性、置信度
以及结论的置信度，没有在渲染阶段重新计算。

源码：[Reviewer](../backend/src/novelty_agent_framework/agents/evidence_reviewer.py)、
[评审字段](../backend/src/novelty_agent_framework/schemas/domain.py)、
[报告绑定](../backend/src/novelty_agent_framework/core/report_binding.py)、
[Renderer](../backend/src/novelty_agent_framework/tools/renderer.py)。

Demo 和测试中还有 0.8、0.9 等固定值，用于演示或构造输入，不是正式评分算法。

## 5. 三个 Validator 问题的来源与复现含义

这三项来自对修改前版本（`48414e56`）的合成输入检查，使用
[现有测试夹具](../tests/test_integrity_gates.py)创建 Work、Artifact、本地文本、Evidence 和 Card，
然后单独改动字段调用 Validator。没有调用真实模型，也不代表已在真实运行中找到同样的坏卡。

### 5.1 Card 的 URL 被替换

保留正确的 Evidence、文件、标题和引文，只把 `card.sources[0].url` 改成无关网址。
原逻辑只要求来源中存在 DOI 或 URL，没有核对 URL 与落盘文献是否一致，所以仍接受。

本次增加机械核验：URL 必须与该引文绑定的 Work/SourceRecord 登记的 URL、落地页或全文地址匹配。
没有可核对记录时拒绝；无关地址、不同路径或查询参数也拒绝。
协议和主机大小写、默认端口、空路径允许做确定性规范化；不联网访问、猜测别名或跟随重定向。
此检查验证的是“与本地记录一致”，不能证明本地记录来自真实权威来源或网址目前可访问。

### 5.2 Card 有 DOI，但本地没有 DOI

在 Card 来源中填写 `10.1234/invented`，Work/SourceRecord 不提供 DOI。
原代码的判断条件是“Card 有 DOI，并且本地 DOI 集合非空，才进行比对”。
本地缺少 DOI 时，比对直接跳过，所以接受了无法核实的值。

本次改为：已填写的 DOI 必须在所绑定文献的本地记录中得到确认；
本地没有 DOI 与已有 DOI 不匹配分别记录拒绝原因。允许 DOI 大小写、`doi:` 与 DOI URL 前缀规范化。
Card 本身没有填写 DOI 时，不强迫所有文献必须有 DOI；合法 URL 仍可作为来源字段。
标题、DOI、URL 必须属于与该来源引文关联的同一 Work，不能从另一篇文献借用字段。

**后续确认：外部核验未解决，暂缓实现。** 用户要求本地没有 DOI 时，应向允许使用的数据库
按 DOI 查询，并核对返回记录是否为同一文献；一致则放行，查询完成但未找到匹配文献则记录
元数据异常。超时、限流和服务不可用应单独记录为核验未完成，不能推断文献异常。
现有 arXiv 精确标识符接口仅支持 arXiv ID，没有 DOI 解析实现。按用户决定，等待允许使用的
数据库接入后再实现，不在本轮新增查询来源。当前本地缺失即拒绝只是临时行为，不证明 DOI 虚假。
该问题已记入[待办清单第 8 节](后端代码审查与待办清单.md#8-validator)。

Card 当前的来源结构没有作者、年份和期刊字段，因此这里没有新增这些字段的逐项比对，
也没有要求不同渠道的元数据完全相同。后续扩展字段时应另行约定确定性的冲突处理规则。

### 5.3 Evidence 的 locator 为空，但 Card 的 location 仍有文字

两个字段分属不同对象，不会自动同步：

```json
{
  "Evidence": {
    "evidence_id": "ev-1",
    "artifact_id": "artifact-1",
    "locator": null
  },
  "Card": {
    "evidence_ids": ["ev-1"],
    "sources": [{"location": "artifact artifact-1 chars:7-27"}]
  }
}
```

上面是关系示意，省略了其他必填字段。复现时只把原本为
`EvidenceLocator(char_start=7, char_end=27)` 的 `Evidence.locator` 改成 `None`，
未改 Card 的位置文字。修复前的字段检查看到 `source.location` 非空就通过；溯源检查遇到
`locator is None` 直接返回，未将那段位置文字重新解析，也未按字符范围核对原文。

这不等于正常 Builder 会遗漏位置：正式 Builder 会用同一组计算得到的字符偏移同时写入
Evidence.locator 和 Card.sources.location。问题在于 Validator 不能仅假设所有输入都始终完整。
后续按用户要求已收紧 Validator：两边位置必须存在且一致，每条来源和 Evidence 都须建立对应；
缺少 locator、只有章节或页码、缺少字符边界、Card 位置文字缺失或不匹配，均拒绝。
不再通过设置 `require_source_location=False` 绕过生产溯源检查。

源码：[元数据与溯源检查](../backend/src/novelty_agent_framework/core/integrity_gates.py)。

### 5.4 locator 留空的历史来源与当前复现结果

进一步追溯发现，旧版 Builder 并不是在传输中丢失位置，而是在构造 Evidence 时明确写入
`locator=None`，构造 Card 来源时明确写入 `location=None`。2026-09-05 的修复提交
`52f1b98b` 加入原文字符区间计算，同时填写两个字段。旧版允许规范化空白匹配引文，
但没有把匹配位置映射回原文，因而主动保留空值。

本次用完全相同的草稿和 Reader 输入，分别执行该提交之前的真实 Builder 源码与当前源码：

| 路径 | Evidence.locator | Card 来源 location |
| --- | --- | --- |
| `52f1b98b^` 的 Builder | `None` | `None` |
| 当前 Builder | `char_start=0, char_end=19` | `artifact art_a chars:0-19` |
| 当前结果经 JSON 序列化、反序列化 | 同上，未丢失 | 同上，未丢失 |

历史[完整流程报告](experiments/MG19333vrw_DeepSeekFlash_FullWorkflowLive/report.md)记录了
当时因位置缺失拒卡的情况及后续修复；[早期工作流实验](experiments/formal-researcher-workflow-smoke/report.md)
也明确记录了旧版的空位置契约。

扫描本地 `outputs/` 的 191 份研究任务产物，发现 389 次 Evidence 对象出现，其中 3 次 locator
为空，均在旧实验 `EXP_FORMAL_RESEARCHER_WORKFLOW` 的同一个文件中，其 Card 的位置也全部为空。
另扫描 `docs/experiments/` 的 233 份研究任务产物，204 次 Evidence 对象出现均有 locator。
这里统计的是对象出现次数，归档可能重复，不是独立任务数；也没有覆盖仓库内所有 JSON 文件。

当前源码中，正常完成、引文纠错和来源拆分都调用同一个 Builder；检查点恢复根据原始读取和
草稿重新编译，不直接信任保存的 Evidence。相关 Builder 和检查点回归 47 项通过。

因此，现有证据支持“旧版主动留空，现已修复”，没有支持“当前正常流程容易丢位置”。
另一层问题已在后续修改中关闭：Schema 仍允许读取历史空 locator，但生产 Validator 会拒绝
缺失或不一致的位置。此前旧数据、外部构造或畸形输入可能进入跳过检查的分支。单独把 locator 清空而保留 location 的案例，
是对该边界的故障注入，不是本次发现的真实生产故障。

## 6. 本次验证与后续问题

新增回归覆盖低分合法卡、非法分数字段、低分且文件损坏的卡、DOI 缺失与不匹配、URL 不匹配与
规范化，以及检查点恢复的卡仍需核验文件。位置门控还覆盖两边置空、缺少完整字符边界、
制品或偏移不一致、多来源中有未配对条目、两边位置一致但指向错误原文等情况。
这些回归测试不调用真实模型，也不重新评估语义质量。

加入位置一致性门控后的全库非 live 回归结果：1379 项通过，4 项既有失败，6 项未选中。
既有失败分别是 3 项 Reviewer 基准缺少历史备份文件，以及 1 项旧搜索工具属性断言。
新增行为的主要测试见[Validator 边界测试](../tests/test_validator_review_boundary.py)和
[检查点测试](../tests/test_evidence_checkpoint.py)。

复现命令（使用 Novelty 环境）：

```bash
NOVELTY_EXPERIMENT_PROFILE= python -m pytest -m 'not live' --tb=short
```

仍需另行决定：

- 是否为置信度、相关性定义统一评分标准，或改用带理由的分档。
- 拆卡后是否应重新判断各篇文献的相关性。
- 如何把贡献归属、比较对象等语义错误接入纠错识别和复核，不能用高分或 Validator 放行替代。
- 若未来支持页码或其他定位方式，应定义与原文可机械核验的映射；当前生产路径要求完整字符位置。
