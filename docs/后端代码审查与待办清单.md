### 0.3 开发顺序与完成判定

先由 P0-02 维护者与各节点负责人核对集中错误码表和所属处理位置，P0-01、P0-06 约定产物索引，并对齐可追溯结果与阶段终态。各 Agent／工具负责人可按已有错误码并行实现当地纠错，无需等待一个集中纠错器；新增或调整码同步更新集中目录及程序定义。Renderer 使用约定的落盘样例开发。P0-05 可先验证门控规则，最终接入须使用实际纠错终态；P0-08 先冻结基线与评价样本，再随各模块就绪执行对照，最后整链路验证。

本轮不自动把整份审查清单都提升为 P0：旧 Web 重建、全量实验目录清理、全部数据库扩展、所有格式的 Renderer、全局配置架构重写仍按原章节状态管理。修复涉及的必要配置、真实运行预算与模型／来源可用性由相应 Issue 记录，不隐去验证阻塞。

### 4.1 Harness：技术停止、恢复控制与工具调用错误

定位结论：下面两类技术停止按统一错误码在所属 Harness／执行控制位置处理，具体恢复调用原 Agent 的既有接口；补检器只读取其最终状态，不执行模型纠错或检查点恢复。该定位只涉及执行层问题，各节点的其他纠错仍在当地实现，不要求都迁入 `ToolCallHarness`，也不能理解为它已经自动恢复所有阶段。

- [ ] 【待处理】迁移 **Reviewer 技术失败／预算耗尽且已有卡时的停止分支**。现位置为 [plan_recovery](../backend/src/novelty_agent_framework/core/recovery_policy.py#L56)；控制归 [ToolCallHarness.run / _run / _finalize](../backend/src/novelty_agent_framework/core/tool_call_harness.py#L157) 所属执行控制层，阶段接入点为 [NoveltyEvidenceReviewer._review_point / review_card / summarize_reviews](../backend/src/novelty_agent_framework/agents/evidence_reviewer.py#L227)。恢复委托 `recover_summary()` → [ReviewerSummaryCheckpoint.attempt](../backend/src/novelty_agent_framework/agents/reviewer_checkpoint.py#L185)，不由补检器重新发研究任务。
- [ ] 【待核对】上述 Reviewer 分支的现状：单卡已使用 Harness，汇总在 `summarize_reviews()` 内直接调用模型，拥有独立超时和一次格式修复；`summarize_with_checkpoint()`／`recover_summary()` 已提供汇总保存与显式恢复。需根据错误码在各自执行位置接通恢复或停止处理，不能假定汇总已经过 Harness，也不能把汇总恢复当作单卡恢复。
- [ ] 【待处理】迁移 **模型超时、传输失败、上下文超限／不可用、输出结构错误时的停止分支**。现位置为 [plan_recovery](../backend/src/novelty_agent_framework/core/recovery_policy.py#L63)；控制定位 [ToolCallHarness._run](../backend/src/novelty_agent_framework/core/tool_call_harness.py#L221) 的模型异常、预算与结束处理，任务接入 [TaskResearcherWorkflow._research / recover_checkpoint](../backend/src/novelty_agent_framework/workflows/research_task.py#L148)。上下文准入事实来自 [evaluate_context_admission](../backend/env/context_admission.py#L79)，结构修复沿用 [repair_json](../backend/src/novelty_agent_framework/core/format_repair.py#L8)；领域输出的具体校验仍由原 Agent 执行。
- [ ] 【待核对】上述模型停止分支的现状：Harness 已记录并抛出模型异常，预算耗尽时可按配置执行预留收尾；`_research()` 保留局部结果，并在 Harness 返回后解析／修复草稿。[EvidenceCheckpointSession.recover](../backend/src/novelty_agent_framework/tools/evidence_checkpoint.py#L143) 只重新核验并恢复已有有效产物，不会续跑模型或工作流。应由执行控制判断恢复、有限重试或停止，不能重置全局预算，也不能把已有恢复接口描述为自动续跑。
- [ ] 【待处理】**工具调用错误**定位 [ResearcherToolRegistry.validate_arguments / execute / execute_validated](../backend/src/novelty_agent_framework/tools/researcher_registry.py#L67) 的工具与参数校验、作用域和执行失败记录，以及 [ToolCallHarness._run](../backend/src/novelty_agent_framework/core/tool_call_harness.py#L438) 的错误反馈和再次调用控制；具体工具处理自身领域错误。已有错误 observation 反馈不等于纠错必然成功，需核对重试输入、验证结果和停止原因；不交给补检器修复参数或工具选择。

## 13. 原任务现场纠错与恢复

已确认的边界：纠错属于原任务的执行闭环，包括必要的继续执行和材料补全；由后置 Validator／Reviewer 发现的问题也应回到对应原任务或评审步骤处理。纠错不新增任务级补检轮次，不以最终证据数量不足为唯一启动条件。已有足够有效卡时，发现的执行问题仍需处理或明确记录其处置结果。

“纠错结束”不等于一定修复成功，而是适用动作已执行并复核，或已有明确的不可恢复、次数／预算耗尽等停止原因。不能仅生成恢复建议就视为完成；也不能为获得有效卡无限重试或放宽校验。

## 14. 任务级补检

已确认的边界：补检是在同一次运行中针对已有查新点追加完整 `ResearchTask`，重新经过 Planner、Researcher、Validator 和 Reviewer，并合并有效成果；不重新解析论文或改写查新点。补检任务本身也需要执行第 13 节的现场纠错。 补检旨在增加一次完整查新机会、降低单次检索的偶然性，不要求一定消除缺口或新增有效卡。验收检查追加任务的实际执行、成果与剩余不确定性的保存以及有界停止，有效卡增量只作为观察指标。

保留三个触发条件，满足任一即可进入补检判断，但实际执行仍受轮次及全局预算等硬限制：

1. **数量不足兜底**：原任务必要纠错结束后，最终有效证据卡数量仍低于配置门槛。包括纠错已执行但仍没有有效卡的情况，不要求先证明存在新的语义研究方向。
2. **Reviewer 语义证据不足**：最新有效 Review 的 `status=insufficient_evidence` 且 `incomplete_reason=semantic_evidence`；数量达标也可触发。单独的补检建议、技术失败或材料不可用不等同于该条件。
3. **查询成功但零候选，需要调整查询**：查新点级，本轮该点至少一条查询成功，且该点本轮所有查询的候选总数为零，不要求全部查询成功。由 Coordinator LLM 生成完整任务、Planner 制定新计划；只有失败、未执行或 partial 不构成成功，任何查询已有候选则不属于本条件。该条件独立于前两条，不因已有历史卡达到数量门槛而被入口过滤。

当前实现：`plan_recovery()` 已移除 `read_artifact`、`fetch_fulltext`、`change_provider`、`retry_request` 的动作选择，只分派任务级 `research_gap` / `replan_query`，并保留停止保护。各节点纠错归属见第 13.1 节，旧逻辑可从 Git 历史查阅；各节点的纠错完成信号尚未接入。

后续接线已完成：三类条件独立检测，按触发码启动独立工作流；同点命中多个码时保留独立决策和任务；`_targeted_supplement()` 已移除，所有任务级动作都由 `Coordinator.plan_supplement()` 调用 LLM 规划。程序校验后回填决策的 coordinator_status / planned_task_ids，再交正常 Planner / Researcher 执行；规划失败停止并保留缺口。协议和工作规范见[任务级补检数据契约与 Coordinator 工作规范](任务级补检数据契约与Coordinator工作规范.md)。现场纠错终态与完整预算门控仍未接齐，不能视为本节整体完成。
